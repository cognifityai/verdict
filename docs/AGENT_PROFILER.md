# Agent Profiler: local workflow and evidence contracts

Verdict combines source-reported usage, typed agent actions, optional selected-scope evaluation, and fixed-case experiments. The same run report accepts imported Claude Code/Codex histories and application agents recorded through `verdict.agent_run(...)`. Capability differences come from the source evidence; a local history import does not automatically provide a genuine provider `Trace`, and provider auto-instrumentation does not automatically provide application task outcomes.

## Synthetic local demo

From an editable checkout with the Verdict and eval packages installed:

```bash
.venv/bin/python examples/agent_profiler_demo.py --database /tmp/verdict-profiler-demo.db
VERDICT_EXPERIMENT_RUNNER=verdict.dashboard.demo_task:run \
VERDICT_EXPERIMENT_CONFIGS='{"baseline":{"version":"baseline-v1"},"candidate":{"version":"candidate-v1"}}' \
.venv/bin/verdict-dashboard --storage sqlite:////tmp/verdict-profiler-demo.db --host 127.0.0.1 --port 8000
```

Choose a fresh database filename; the generator refuses to overwrite a file. Open `http://127.0.0.1:8000/dashboard`. The sample contains a wholly synthetic three-turn coding session across two runs with reported input/output/cache counters and a recorded failed test, plus an application-agent run produced through the SDK. No provider key or network call is required. The **Evaluate → Saved Cases** sample routes a critical incident and a routine edit. The baseline fails to page on the critical incident but handles the routine edit; the candidate fixes paging but wrongly pages for the routine edit. Run this comparison explicitly. Its checks are deterministic and synthetic, not evidence of a live model improvement.

## Usage and run report

**Overview → Summary** shows monitoring status first, followed by two charts when agent turns are captured: reported tokens by UTC day and affected runs by recorded issue type. Select a day to show its sessions, then select a session to see its five largest displayed turns and run links. Expand the remaining turns or open the session report when needed. Select an issue bar to open its affected runs. Issue categories can overlap; their bars are scaled to the largest displayed issue count rather than parts of a whole. If no usable token totals were captured, the chart says so and offers a path to inspect the sessions with missing totals. Expand **Evidence gaps** to see where capture limits what Verdict can conclude. A historical monitor check appears as one status, not as individual metric rows. It is a saved comparison, not an active alert or a task-quality judgment. **Open Monitor details** shows the full per-metric comparison. Technical coverage remains under an expandable section.

Open **Overview → Performance**, select a UTC day, then a source/session. The chart shows reported input, output, cache, and total tokens where available, model attribution, estimated API list price, and coverage. Provider model-call aggregates are under **Model-call diagnostics**. Source-reported totals are authoritative where valid. Cache and reasoning subtotals are not summed into them again. Codex cumulative counters are converted to per-turn deltas only when source identity and ordering support that conversion. A missing total stays unknown at every level, even when known input and output components support a list-price estimate for one model and usage basis. Mixed, missing, or unrecognized models are left unpriced. A subscription charge cannot be inferred from this view.

The selected session report combines all runs sharing its source-qualified session identity, including requests and outcomes, usage coverage, event timeline, findings, suggested actions, and saved historical evaluations, which may reflect earlier evidence. A complete report covers up to 20 runs, 20 turns, and 80 events. Larger sessions show a bounded partial view with up to 20 turn excerpts, 80 event headers, and source-reported token totals for the displayed run slice; whole-session judging, findings, and list price are withheld. Open a linked run in **Explore → Agent Runs & Tools** for deeper evidence. Evidence references point to actual turns or events. A failed tool or test suggests inspection, not proof that all subsequent work was wasted. The run's elapsed span is not model latency.

Suggestions currently flag an unresolved recorded test failure, repeated tool errors, sustained reported input growth across turns with one token basis, and repeated large captured tool results. Input growth requires at least three nondecreasing reported inputs, with the last at least 10,000 tokens and twice the first. A repeated result must appear at least twice and contain at least 2,048 characters. These are review triggers, not measured waste: growing context may be useful, cached input may be cheaper, and repeated reads may be necessary. Each suggestion links to the observed turns or events and recommends checking a smaller alternative against the same task checks before changing a workflow. Verdict does not infer which files consumed tokens or claim a savings percentage from these rules.

## Analyze and evaluate one scope

**Analyze turn** runs a local deterministic inspection. It requires no judge key and can report a partial capture. **Evaluate this turn** and **Evaluate this model call** on a selected genuine Trace route to Evaluator Lab with that exact selection. Changing the evaluation unit clears the selection and approval. **Evaluate this session**, **Evaluate this run**, and **Evaluate tool action** produce an exact bounded redacted preview before an external judge call. The preview shows scope, criterion/rubric, model, resolved destination, evidence, coverage, one planned call, and a static price estimate when available. Approval is tied to its fingerprint; a changed criterion, destination, or evidence requires a new preview. No page load automatically invokes a judge.

A session evaluation uses ordered evidence from every included run and requires at most 20 runs, 20 turns, 80 events, complete request/final-response evidence, and at most 8,000 redacted evidence characters. It is one evaluation of the whole session, not an average of turn grades. A run evaluation has the same turn, event, content, and character bounds for one run. An oversized or incomplete scope reports the first known unavailability reason with empty evidence text and no judge call. A tool-action evaluation requires the recorded task, usable tool contract/options text, explicit arguments (including valid empty arguments), and one unambiguous matching call/result pair. An observed plan can be evaluated as a criterion; Verdict does not infer hidden planning. Missing, redacted, truncated, or ambiguous evidence is marked unavailable rather than scored as complete. The scoped judge is asked to cite exact `[turn:...]` or `[event:...]` references. Fabricated turn/event references are rejected; other bracketed prose is ignored as a citation. An uncited grade is labeled an uncited judge opinion rather than an evidence-linked finding. Stored results include scope, evaluator and evidence fingerprints, coverage, criteria, verdicts, and evidence references. `PASS`, `FAIL`, `UNCLEAR`, judge error, and not-run are different states.

The UI's estimate is a static list-price estimate, not a billing cap. Provider SDK retry behavior can make actual billing higher. The local demo does not run a paid provider. For live BYOK testing, configure the chosen provider key in the dashboard process, preview synthetic evidence, and approve the one call. Calibrate an evaluator against your own held-out labels before treating scores as reliable.

## Saved cases and change comparison

**Evaluate → Saved Cases** accepts 1–10 reviewed cases with a runnable input, expected behavior, optional relevant context, and exact/contains/not-contains output checks. From **Explore → Agent Runs**, **Draft a reviewed case from this run** copies the first complete, already-redacted captured request into a new unsaved draft. If no complete request exists, the input remains blank. Review and edit the input for the configured runner, supply expected behavior and a check, and explicitly confirm review before saving. User-authored case fields are stored and passed to the configured local runner exactly as entered; remove secrets and private data before saving. Capture alone cannot establish the right answer. Verdict never executes commands copied from a Claude/Codex history automatically. Saving a case set creates a local versioned record. Experiment and scoped evaluation results are immutable records and cannot be rolled back through the control API.

The dashboard process must explicitly configure `VERDICT_EXPERIMENT_RUNNER` as `python.module:function` and `VERDICT_EXPERIMENT_CONFIGS` as a JSON object of named, versioned baseline/candidate configurations. The trusted function receives `(input, context, configuration)` and returns an output string or `{"output":"...", "usage":{...}, "costUsd":0.01, "costBasis":"provider_bill"}`. Each side uses the same saved cases and fixed checks. `VERDICT_EXPERIMENT_TRIAL_TIMEOUT_SECONDS` sets the host trial limit from 1 to 300 seconds (default 120); the effective value is displayed in the UI. The synchronous endpoint rejects a comparison before invoking the runner when cases × two sides × trials per side × configured trial timeout exceeds 600 seconds of runner time. Process cleanup and storage may add time; this is not a strict HTTP deadline. Use fewer cases/trials or a shorter host timeout to fit; one case with one trial per side can use the 300-second maximum. Output is bounded, and timeout stops the worker's ordinary POSIX process group before the next trial. This is process cleanup, not containment of deliberately detached processes or a security sandbox. Choose 1–3 trials per side. Saved comparisons can be reopened from recent history without rerunning the application. Verdict records configuration versions/fingerprint, case-set revision, evaluator identity, each trial's output, reported usage and cost if supplied, task elapsed time, errors, and fixed/regressed/unchanged/unverified groupings. It displays average runner elapsed time for verified trials and application-reported cost only when every trial on both sides uses one matching cost basis. Task elapsed time is wall time for the runner, not model latency. Application-reported cost is not independently verified by Verdict.

The runner is trusted host configuration, not user-submitted code. Run it against disposable or otherwise approved resources: Verdict cannot guarantee the runner itself has no side effects or that its initial state and external responses are equivalent. Checks test the specified output behavior only. Include cases that already pass to find collateral regressions, and repeat trials when nondeterminism affects the decision.

## Scheduled analysis

**Monitor → Schedule** stores an opt-in local schedule. `verdict-service --storage sqlite:///./verdict.db --once` executes one cycle; without `--once`, it repeats at the saved interval. A schedule can rescan explicitly approved local history paths, or use **Analyze already captured agent activity** for SDK/incoming evidence with no local history path. Empty source fields are treated as absent in both saved and manual cycles. Each cycle runs persisted deterministic analysis. An existing prospective genuine model-call monitor may be advanced if explicitly selected. Cross-process cycle locking prevents overlaps. The SQLite lock requires POSIX; on other platforms use PostgreSQL for scheduled cycles. The manual `POST /api/control/actions/run-schedule` uses the same cycle and returns a specific unsupported-platform error for non-POSIX SQLite. Notification delivery uses stored idempotency keys and requires an independently configured local log or webhook destination.

Agent-session comparisons are descriptive and do not produce statistical drift alerts. The prospective model-call monitor keeps its minimum-sample, stable-evaluator, and multiple-testing rules; see [statistics](STATS_PRIMER.md). For a bounded session, run, or tool action, the preview also offers **Queue one evaluation** for Anthropic or OpenAI. Review the exact evidence, destination, criterion, and conservative static list-price bound, set a maximum approved static estimate, and explicitly authorize one later call. Both the local service and the manual run-cycle endpoint can consume that pending approval and make the one external judge call; triggering a cycle is therefore an egress action when an approval is pending. The approval is spent before the provider call and never retried after an interrupted or timed-out attempt. A completed result or saved judge error is linked to the spent job and can be reopened without another provider call; an interrupted reserved attempt remains outcome unknown. Changed evidence cancels the approval before egress, and a pending approval can be cancelled in the same panel. Both Verdict and provider SDK retries are disabled for this path. The static estimate limit is not an invoice guarantee: provider pricing or billing can differ. Google and Jev are not supported for scheduled judging. Deterministic capture and analysis retry safely from stored evidence after an interrupted cycle; a consumed external approval does not.

## Privacy and support boundaries

Prompts, tool outputs, and judge replies are untrusted content. Verdict applies bounded, best-effort redaction before storage and before a scoped external preview. Review the exact preview before egress. Do not put credentials, customer traces, or private paths into saved case sets or screenshots. Explicit application-agent capture supports Python SDK contexts and existing documented transports; Claude Code/Codex are the first automatic local-history imports. No universal task correctness, automatic token savings, multi-agent causal attribution, or automatic connector support is implied.
